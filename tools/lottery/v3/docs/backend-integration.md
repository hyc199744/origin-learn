## 已对接的现有协议

| 操作 | 当前协议 | 前端行为与限制 |
|---|---|---|
| 查询邀请关系 | `GET /me?addr=<wallet>` | 校验地址、邀请人、统计数字、币种精度与原始金额；查询失败时不当作零余额 |
| 获取短码 | `GET /code?addr=<wallet>` | 只展示有效的 6 位大写字母/数字短码 |
| 解析短码 | `GET /resolve?code=<code>` | 替换当前待确认邀请人，用户核对后才签名 |
| 官方邀请候选 | `GET /health` 的 `defaultRef` | 只作为候选，不静默绑定、不视作已绑定 |
| 绑定 | `POST /bind`，`{invitee,inviter,sig}` | 保留现有签名格式；提交后重新读取 `/me` 确认，不信本地放行标记 |
| 领取平台返佣 | `POST /claim`，`{addr,sig}` | 只提示请求受理，不把 HTTP 成功当作已到账；当前协议缺少前端可依赖的最终状态查询 |
| 彩票旧返佣 | 各 V3 合约的查询与领取 | 与平台服务账本分开，不相加、不擅自迁移 |
| 卡牌退款 | 各游戏合约 `withdrawable` 与 `withdraw` | 直接查询链上余额，领取不依赖邀请码或对战会话 |

`/me` 当前结构：`{addr,referrer,directCount,indirectCount,earned,claimed,claimable,invitees,tokens,rates}`。金额应为最小单位的十进制整数字符串；`tokens` 元数据为 `{sym,dec}`。前端不把不同币种求和。

现有签名文本：

```text
ANUBIS PLAY invite: bind <invitee> -> <inviter>
ANUBIS PLAY claim rewards: <wallet>
```

以上兼容格式不证明服务端已经具备域名绑定、nonce、时效或抗重放能力，发布前必须核查服务器实现。

## 对账口径

- 游戏：每个币种分别核对用户实际投入、底池、手续费、赢家实际到账和退款；不得用 `底池 × 97%` 替代实际结算。
- 返佣：从实际平台手续费分成；来源事件、上级关系快照、规则版本和金额一起保存。旧 V3 返佣与服务返佣不能重复入账。
- 领取：`累计确认返佣 = 已确认领取 + 已冻结领取 + 可领取`，不得以成功请求数量计算已领取。
- 彩票历史：按购票交易中的实际代币转账计算成本；缺少转账凭证时为待核对，不用现票价倒算。
- 大历史量：服务器做增量索引、分页和重组回滚。前端现有浏览器索引查询只是兼容读取，不替代长期账本服务。

## 接入顺序与最终验收

1. 提供服务器项目路径和可审查源码/仓库副本、启动方式、反代路由、数据库结构及现有脱敏接口示例。不要在聊天或仓库提供密码、私钥、助记词或密钥文件。
2. 核查 B01–B09，建立隔离测试环境。修改签名协议时保留显式版本协商，旧签名不得被用于新版本的另一用途。
3. 用本地或隔离测试代币验证：新用户绑定；旧用户冲突；拒绝签名；钱包/网络切换；四币种入座、结算、退座、退款；断线、刷新、并发重试；返佣记账和领取；任务中途重启；RPC/索引器失败；开奖区块过期。
4. 每个用例同时留存界面状态、operationId、交易回执和账本分录。浏览器显示“成功”不能作为单独验收证据。
5. 用户在另一设备登录，历史与可领余额一致；重放同一请求和同一事件不增加支付或返佣。
6. 审核通过后再按仓库流程合入 dev、用户验收、申请生产发布。需要真实钱包操作时由用户本人在自己的钱包中完成。

只有服务器源码审查、隔离端到端验收和对账均完成，才能将本任务标记为“全平台闭环完成”。
